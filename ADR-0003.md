# ADR-0003: Hand-written SQL migrations; no ORM

## Status

Accepted

## Context

_Reference Implementation Strategy_ (Doc 17), Section 3, fixes the physical storage strategy: an append-only event log as the source of truth (one row per committed generator application — Capture, Supersede, Interpret, or a Synthesis batch), with the materialized `E`/`I` tables (`elements`, `coordinate_values`, `dimensions`) maintained as a derived, rebuildable read-index that Subsystem 1 itself keeps current. Section 4 fixes SQLite as the engine. Neither section fixes how the schema for these tables is defined, versioned, or evolved as the project matures — nor whether a query-building or object-relational layer sits between _[[16-Subsystem-Interface-Contracts]]_'s `PersistentResearchState` interface and the actual SQL.

## Decision

Schema is defined and evolved via **hand-written, sequentially numbered `.sql` migration files** (`0001_init.sql`, `0002_...sql`, ...), applied in order at startup by a small custom runner that compares a `schema_version` table against the highest available migration number. `PersistentResearchState`'s implementation issues parameterized SQL directly against `better-sqlite3`'s prepared-statement API — **no ORM, query builder, or schema-mapping library** (Prisma, Drizzle, Kysely, TypeORM, or similar) sits between the interface and the database.

## Why not an ORM

_[[15-Canonical-Data-Model]]_'s "Full Type Summary" is a small, closed, already-fully-specified schema — an ORM's core value proposition (generating queries across a large or evolving object graph, managing arbitrary relations the codebase doesn't yet know about) has no purchase here, since there is nothing left to discover about the shape of the data; Document 15 already closed that question. More specifically, several of Documents 15/16's requirements are exactly the kind an ORM's abstraction layer tends to obscure rather than assist:

- **E3's acyclicity check** (_[[15-Canonical-Data-Model]]_ — walking a `supersedes` chain backward from a candidate `old` element, bounded by construction since every step mints a fresh identity) is a specific, small recursive query most ORMs would either not express cleanly or would translate into something less auditable than the equivalent hand-written recursive CTE.
- **`Current(E)` and `Conflicts(S)`** (Doc 15's "index-backed views, not scans") are most naturally maintained as SQL indexes/views directly against the `elements`/`coordinate_values` tables — an ORM's relation-mapping layer would typically compute these in application code from loaded objects, defeating the point of an index-backed derivation.
- **Auditability of the D10 legality gate.** D10.1–D10.4 are, per Doc 15, partly structural (enforced by the type system) and partly checked at runtime (E1–E3). Keeping the SQL that enforces the checked half hand-written and adjacent to the interface method that calls it (`commit`, per _[[16-Subsystem-Interface-Contracts]]_) means a reviewer can read the exact SQL responsible for each condition, line by line, without first understanding an ORM's query-generation behavior. For a system whose entire premise is that its correctness is provable against a fixed set of theorems, this auditability is worth the extra boilerplate.

## Consequences

- More boilerplate per query than an ORM would generate; accepted deliberately, as argued above.
- Migrations are plain, reviewable SQL files, checked into version control alongside the code that depends on them; the runner is a small, first-party utility (a loop comparing `schema_version`, not a third-party migration framework), since the migration needs here are simple linear application, not branching/rollback support a general migration tool is built for.
- Any future move to a different SQL engine (per ADR-0002's noted possibility of a WASM backend) requires re-verifying that the hand-written SQL's syntax and recursive-query support are engine-compatible — a cost an ORM's abstraction layer might have absorbed, and one this ADR accepts explicitly as the trade-off for auditability now.
