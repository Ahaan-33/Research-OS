# ADR-0009: Build better-sqlite3 for Electron in an isolated, non-pnpm directory — never rebuild the workspace's shared copy in place

## Status
Accepted

## Context

After ADR-0007/ADR-0008 landed, the build (`pnpm run build`) succeeds, but
`pnpm test` started failing:

```
NODE_MODULE_VERSION 140
This version of Node.js requires NODE_MODULE_VERSION 127.
...
Module did not self-register
```

**Root cause.** The workspace has exactly one physical copy of
`better-sqlite3` on disk. `pnpm-workspace.yaml` includes both
`packages/core` and `packages/obsidian-plugin`, both depend on
`better-sqlite3`, and pnpm's content-addressable store deduplicates that
into a single package instance under
`node_modules/.pnpm/better-sqlite3@12.11.1/...`, symlinked into both
packages' `node_modules`. Confirmed directly:

```
node_modules/core/node_modules/better-sqlite3       -> node_modules/.pnpm/better-sqlite3@12.11.1/node_modules/better-sqlite3
node_modules/obsidian-plugin/node_modules/better-sqlite3 -> node_modules/.pnpm/better-sqlite3@12.11.1/node_modules/better-sqlite3
```

There is one `build/Release/better_sqlite3.node` file, and it is shared by
**two consumers with incompatible ABI requirements**:

- `@ros/core`'s Vitest suite runs under plain Node (ABI 127 in this repo's
  Node 22) and loads the addon via `better-sqlite3`'s own default
  `bindings()` auto-resolution (no `nativeBinding` override — ADR-0007
  intentionally leaves that path alone for the test suite).
- The Obsidian plugin runs under Electron 39.8.3 (ABI 140) and needs a
  binary compiled against Electron's headers, not Node's.

`@electron/rebuild`, run the way the earlier "Completed" work described
("rebuilt the native addon against Electron 39.8.3 using
electron-rebuild"), rebuilds a module **in place** inside whatever
`node_modules` directory it's pointed at. Pointed at the workspace root
(the natural thing to do), it overwrote the one shared
`better_sqlite3.node` with an Electron-ABI build — which is exactly what
the Obsidian plugin needs, but it is the *same file* Vitest's
`better-sqlite3` import also resolves to. Fixing Electron loading this way
necessarily breaks Node loading; there is no in-place ordering of "rebuild
for Electron" and "rebuild for Node" that satisfies both, because both
resolve to one path.

This is a structurally different problem from ADR-0007/ADR-0008: those
were about a bundler/host losing track of *where* a correct, single
binary lived. This is about the workspace needing **two different,
simultaneously-valid binaries** for the same dependency — a single-file
resolution model (pnpm's dedup, `better-sqlite3`'s own `build/Release`
convention) cannot hold both.

## Decision

Give the Electron build its own physically separate copy of
`better-sqlite3`, installed by a package manager invocation that pnpm's
workspace resolution and deduplication never sees:

```
packages/obsidian-plugin/native/electron-better-sqlite3/
  package.json          # pins better-sqlite3, NOT a pnpm workspace member
  node_modules/          # created by plain `npm install`, isolated
```

`packages/obsidian-plugin/native/electron-better-sqlite3` is deliberately
*not* listed under `pnpm-workspace.yaml`'s `packages/*` glob in a way that
lets pnpm hoist/dedupe it — its `better-sqlite3` is installed with `npm`,
not `pnpm`, into its own free-standing `node_modules`, so it can never
become the same physical file as the workspace-hoisted copy no matter
what pnpm does elsewhere.

`scripts/rebuild-native-for-electron.mjs` (run via
`pnpm run build:native:electron`) is the only thing that touches this
directory:
1. `npm install` inside it (isolated from pnpm entirely).
2. `@electron/rebuild`'s `rebuild()` API, scoped to that directory
   (`buildPath`), targeting the Electron version read from the root
   `package.json`'s own `devDependencies.electron` pin (single source of
   truth, no hardcoded version to drift).
3. Verifies the resulting `.node` file exists before declaring success.

It also checks that the isolated directory's `better-sqlite3` version
pin matches `@ros/core`'s, failing loudly on drift rather than silently
shipping a build of a different version than the one the rest of the
workspace (and its tests) actually exercise.

`esbuild.config.mjs`'s addon-copy step now sources from this isolated
directory instead of `require.resolve('better-sqlite3/package.json')`
(which would have resolved to the shared, pnpm-hoisted, Node-ABI copy —
the same mistake that caused this bug). If the isolated build hasn't been
produced yet, the build fails immediately with a message pointing at
`pnpm run build:native:electron`, rather than silently shipping a stale or
wrong-ABI binary.

The workspace-root `better-sqlite3` (`node_modules/.pnpm/...`) is now
**never** touched by any Electron-targeting step. It stays exactly as
`pnpm install` (via `prebuild-install`/`node-gyp`) built it: for Node's
own ABI, which is what Vitest needs.

Verified end-to-end: `pnpm test` passes (20/20) both before and after
running `pnpm run build:native:electron`; `pnpm run build` produces a
`better_sqlite3.node` next to `main.js` that is a byte-for-byte different
file from the workspace-hoisted one (confirmed via checksum) and reports
Electron's ABI, not Node's.

## Why not use `@electron/rebuild`'s own isolation options against the workspace root

`@electron/rebuild` can be pointed at an arbitrary `--module-dir`, but
that only changes *which* `node_modules` it scans for modules to rebuild
in place — it does not create a second copy for you. Pointed at the
workspace root, it rebuilds the one shared file (today's bug). There is no
flag that says "build a second, parallel binary here without disturbing
the first"; the only way to get two binaries is two separate package
installs, so that's what this ADR does explicitly.

## Why not keep one binary and give it a build-time flag / feature detect the runtime

Rejected because `better-sqlite3` ships a compiled native addon — ABI
compatibility is a property of how the binary was compiled (against which
V8/Node headers), not something a runtime flag can paper over. A single
`.node` file is fundamentally either Node-ABI or Electron-ABI; there is no
"works for both" build of the same file.

## Why not have Vitest itself load the Electron-built binary via `nativeBinding`

Rejected: that would require running the *test suite* inside Electron's
Node runtime (Electron's bundled Node, ABI 140) instead of plain Node,
which is a much larger change to CI/dev tooling than isolating one
dependency's build output, and would leave contributors unable to run
`vitest` with a plain `node`/`npm test` locally the way ADR-0002 already
assumes for v0.

## Consequences

- New build step, run less often than `pnpm run build`: whenever
  `better-sqlite3`'s pinned version or the `electron` devDependency
  version changes, `pnpm run build:native:electron` must be re-run before
  `pnpm run build`. This mirrors how ADR-0007 already treated the addon
  as machine/version-specific, single-platform, v0-scoped build output —
  not something regenerated on every build.
- `packages/obsidian-plugin/native/electron-better-sqlite3/node_modules`
  and its `package-lock.json` are build output, not source; gitignored.
- `packages/core`'s Vitest suite and the workspace root's `better-sqlite3`
  are permanently insulated from anything ADR-0007/ADR-0009's Electron
  tooling does — no script in this repo touches the pnpm-hoisted copy.
- Any future native dependency needing both a Node-ABI (test) and
  Electron-ABI (shipped) build should follow this same shape: an isolated,
  non-pnpm install directory under `packages/obsidian-plugin/native/`,
  built by its own script, sourced explicitly by `esbuild.config.mjs` —
  never rebuilt in place inside the shared workspace `node_modules`.
