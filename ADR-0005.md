# ADR-0005: Vitest + property-based testing (`fast-check`) for algebraic conformance; conventional unit tests for everything else

## Status

Accepted

## Context

ADR-0001 already names Vitest as a shared dev dependency without a dedicated rationale document. Separately, several documents in Phases 4–6 state conformance obligations that are not ordinary "does this function return the right value for this input" unit tests, but claims about a *property* holding across all inputs: idempotence of Interpret (_[[07-Transformation-Algebra]]_, G3 table), the join-semilattice laws for `E` and the multi-value-register merge laws for `I` (_[[06-Research-State-Mathematics]]_, T1–T2), the `PosBool(Acts)` absorption/commutativity/associativity laws (_[[14-Provenance-Structure]]_, Theorem P1), and the rebuild-and-diff conformance check _[[02-System-Invariants]]_ and _Reference Implementation Strategy_ (Doc 17, §3) both call for ("rebuild the materialized tables from the log and diff against the live tables — should always be empty"). None of these are naturally expressed as a fixed list of example-based test cases; each is a universally-quantified claim the implementation must satisfy for arbitrary legal input, which is precisely what property-based testing is for and unit testing, by construction, cannot cover exhaustively.

## Decision

**Vitest** as the test runner (already implied by ADR-0001), for both conventional unit/integration tests and property-based tests. **`fast-check`** as the property-based testing library, used specifically — and only — to encode the algebraic properties named above as executable, randomized-input tests, generating arbitrary sequences of `Capture`/`Supersede`/`Interpret` operations (respecting D10's preconditions, so generated sequences are always well-formed candidate inputs) and checking the proven property against every generated sequence.

Concretely, four property suites are established as the conformance backbone, each directly citing the theorem it encodes:

1. **Join-semilattice laws for `E`** (T1) — generate two independently-grown `EvidenceSet` values from arbitrary Capture sequences; assert `merge(A,B) = merge(B,A)` (commutativity), `merge(A,A) = A` (idempotence), and `merge(merge(A,B),C) = merge(A,merge(B,C))` (associativity), where `merge` is the concrete implementation backing `⊔`.
2. **Multi-value-register laws for `I`** (T2) — generate arbitrary sequences of `Interpret` calls, including deliberately conflicting writes to the same `(element, dimension)` pair; assert pointwise-union behavior holds and that a conflicting write never causes the losing value to disappear (the concrete, executable form of INV-6/INV-19).
3. **Interpret idempotence** (G3 table) — generate an arbitrary legal state and an arbitrary `(e,d,v)` triple; assert `interpret(interpret(s,e,d,v), e,d,v) = interpret(s,e,d,v)`.
4. **`PosBool(Acts)` absorption/commutativity/associativity** (_[[14-Provenance-Structure]]_, Theorem P1) — generate arbitrary finite sets of atomic act references and arbitrary `⊗`/`⊕` compositions; assert the semiring laws hold on the concrete `ProvenanceExpr` representation, directly exercising the antichain-with-absorption implementation against the axioms Document 14 proved abstractly.

The **event-log-replay conformance check** (Doc 17, §3) is implemented as an integration test, not a property test — it runs against realistic recorded fixture logs (captured from exploratory manual use, checked into the test suite) rather than generated ones, since its purpose is regression detection against real accumulated data shapes, not universal quantification over synthetic ones; this is a deliberate difference in testing style from the four property suites above, not an oversight.

## Why property-based testing specifically, rather than a larger fixed set of hand-written unit test cases

A hand-written unit test can assert "Interpret is idempotent for *this* specific `(e,d,v)`" — it cannot, by construction, assert the theorem itself, which is a universally-quantified statement. Given that Documents 06, 07, and 14 already did the work of proving these properties hold for the *mathematical* objects, the corresponding engineering obligation is to verify the *implementation* actually realizes the same objects — and the only testing technique that checks a universal claim rather than a finite sample of it is generating a wide, randomized space of inputs and checking the property on each. This is not a stronger claim than "these tests passed" would otherwise support (property-based testing does not constitute a proof, and is not offered as one — the proofs already exist in Documents 06/07/14) — it is the correct-strength verification that the code matches proofs already established elsewhere, which is a different and more targeted goal than general test coverage.

## Why not a formal verification tool (e.g., TLA+, or a dependently-typed re-implementation) instead

Considered, for the same four properties. Rejected for v0: _Reference Implementation Strategy_'s own stated goal is the smallest implementation that validates the architecture through real use, not a machine-checked proof artifact — introducing a formal verification toolchain would be exactly the kind of scope this project's Method (_[[12-System-Architecture-First-Draft]]_) already warns against taking on before it's forced. Property-based testing is the correctly-scoped middle ground: stronger than example-based unit tests, without requiring a second, separate formalization effort parallel to the one already completed in Documents 06–11.

## Consequences

- `fast-check` becomes a shared dev dependency at the workspace root (per ADR-0001's hoisting convention), used only within `@ros/core`'s test suite — the Obsidian plugin shell has no algebraic properties of its own to property-test and is covered by conventional integration tests against the fixed `TransformationEngine`/`ProjectionEngine` interfaces instead.
- Property-based test failures report a shrunk minimal counterexample (a `fast-check` feature) — any future failure here is a direct, actionable signal that the implementation has diverged from a specific, named theorem in Documents 06, 07, or 14, and the failing test's name should always cite which one, so a counterexample is legible against the formal document that predicted it shouldn't exist.
- This test suite is the concrete, executable form of Documents 06/07/14's proofs — but it is not a substitute for them, and a passing suite does not license revising or discarding the corresponding formal document; the proofs remain the authority, the tests are evidence the code agrees with them.
