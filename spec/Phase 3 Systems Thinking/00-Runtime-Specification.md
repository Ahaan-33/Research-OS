## Purpose

Every prior document (Phase 1 Philosophy, Phase 2 Architecture, _Computational Principles_, _Computational Model_, _Convergence Pass_, _Discovery Roadmap_) establishes **what exists** and **who may change it**. None of them establish **when**. This document is the missing temporal axis: it specifies the runtime — the living process that turns idle silence, a keystroke, and a periodic Synthesis run into the same underlying algebra of `S = (E, I)` evolving through legal morphisms.

This document assumes the reader has internalized:

- the two authoritative planes (Evidence, Interpretation) and the six converged components (_[[Convergence Pass]]_),
- the four endomorphisms — Capture, Supersede, Interpret, Synthesize — and three read-only functors — Project, Local Intelligence, Relationship/Emergence (_[[Discovery roadmap]]_),
- the contract table governing who may write where (_[[System Architecture - Division of Responsibility]]_).

It introduces no new authority. It only asks: at what cadence, in what order, and under what triggers does each already-legal transition actually fire?

References forward to: _[[01-State-Model]]_ (what the runtime operates on), _[[02-System-Invariants]]_ (what the runtime must never violate), _[[05-Design-Review-Stress-Test]]_ (where this model is attacked).

## Core Concepts

### The Runtime Is Two Loops, Not One Pipeline

The _Computational Model_ document already describes "the long cycle" (evidence → synthesis → interpretation → emergence → projection) and "the two fast lanes" (direct Capture, direct Interpret). The runtime's entire job is to keep both moving without either blocking the other:

- **The Interactive Loop** — sub-100ms, foreground, one object at a time. Every keystroke, capture, metadata edit, and navigation query lives here. It never waits on Synthesis or on Emergence recomputation.
- **The Reconciliation Loop** — seconds-to-minutes, background, many objects at a time. Synthesis, full Relationship/Emergence recomputation, and Local Intelligence indexing live here.

These loops share the Substrate but never share a clock. A slow Reconciliation pass must never stall a keystroke. A fast Interactive write must never be blocked waiting for Reconciliation to "catch up" — the two planes are always in _some_ legally valid state, and a Projection rendered mid-Reconciliation is simply a Projection of an earlier, still-valid `S`.

### Everything Renders From `S`; Nothing Renders From Progress

At any instant, exactly one of two things is true about anything visible on screen: it is a direct fact from `E` or `I` (an evidence object, a metadata coordinate), or it is the output of a pure function of the current `S` (a Projection, a graph edge, a suggestion). The runtime never allows a third category — "something computed from an intermediate, uncommitted state" — to reach the Surface plane. This is what makes idle-state and mid-recomputation-state visually indistinguishable to the researcher except in staleness, never in kind.

## Formal Definitions

### Runtime State Vector

At any instant `t`, the running system holds:

```
Runtime(t) = ⟨ S(t), Session(t), Cache(t), Queue(t) ⟩
```

- `S(t) = (E(t), I(t))` — the authoritative Research State (Substrate). Persistent.
- `Session(t)` — Lifecycle Orchestrator state: zero or more in-progress Investigations, each an unevaluated pre-formal "thunk" not yet admitted into `S` (_Discovery Roadmap §7_). Ephemeral, process-scoped.
- `Cache(t)` — every derived structure: Relationship/Emergence graph, Local Intelligence indices, Projection render caches. Fully a function of `S(t)` (and, for Local Intelligence, its own deterministic internal parameters); safely discardable at any `t`.
- `Queue(t)` — pending work: unprocessed Capture events awaiting indexing, a scheduled Synthesis run, a dirty Cache region awaiting recomputation. Ephemeral.

Only `S(t)` is unrecoverable if lost. Everything else can be regenerated by re-deriving from `S(t)` and, where relevant, resuming an interrupted Investigation from its last checkpoint (see _Crash Consistency_, below) — with the explicit exception that in-progress Investigation content that was never checkpointed is legitimately, by design, lost (_Convergence Pass_, Lifecycle Orchestrator caveat).

### Event

An **Event** is the atomic unit the runtime schedules. Every event carries:

```
Event = ⟨ kind, payload, origin, timestamp, causality_token ⟩
```

`kind` ∈ { Capture, Interpret, SupersedeDeclare, IntentSubmit, SynthesisRequested, IndexRequested, ProjectionRequested, SessionTransition }.

`causality_token` references the version of `S` (or `Session`) the event was formed against — this is what lets the runtime detect whether an Interpret event is still valid to apply (see _Invalidation Rules_) after concurrent activity.

### Tick

The runtime is not literally continuous; it is **event-driven with a bounded idle tick**. Absent any Event, a low-frequency idle tick (order of seconds) checks only two things: whether a Synthesis schedule has elapsed, and whether any Cache region is dirty and the machine is otherwise idle enough to recompute it speculatively. This is the entire idle-state runtime — see next section.

## Runtime Lifecycle

### What Exists When the Software Is Idle

At rest, with no researcher input and no background work pending:

- `S` sits on persistent storage, fully materialized, requiring no active process to remain valid.
- `Cache` may be entirely cold (nothing computed) or entirely warm (everything computed as of the last activity) — both are legal idle states. The runtime makes no promise about which.
- `Queue` is empty.
- `Session` may be non-empty: an Investigation can sit indefinitely mid-arc (e.g., a hypothesis awaiting an experiment scheduled for tomorrow) without this counting as "unfinished work" the runtime is obligated to advance. Idle Investigations are simply unresolved thunks, exactly as valid at rest as in motion.
- Exactly one thing may legally be running: the idle tick, checking the Synthesis schedule.

This is the direct runtime consequence of "no sessions" (per the governing invariants in _Untitled.md_): there is no notion of an active vs. inactive _application_ session distinct from the Lifecycle Orchestrator's own investigation-level sessions. The process can be killed and restarted at any idle instant with zero semantic difference — this is not an aspiration, it follows directly from `Cache` and `Queue` being empty and `S` being the only thing that must survive.

### Startup

1. Load `S` from persistent storage (Evidence Plane, Interpretation Plane). This is the only step that can fail in a way that matters — if `S` is unreadable, startup halts and reports rather than guessing (see _Failure Recovery_).
2. Load `Session` — any Investigations that were mid-arc at last shutdown, from their last checkpoint (see _Crash Consistency_).
3. `Cache` starts cold by declaration — it is never trusted from a previous run without integrity verification. It is deterministically re-derivable, so re-deriving lazily (see _Lazy Evaluation_, below) is always cheaper and safer than trusting a serialized cache that may not match the current `S`.
4. `Queue` starts empty.
5. Only once step 1 succeeds does the runtime accept new Events. Steps 2–4 may proceed concurrently with the researcher beginning to Capture — a Capture event never depends on Cache being warm.

### Shutdown

There is no shutdown procedure the researcher must invoke (_Experience Constraints §"Ending Work"_). What the runtime must guarantee is that shutdown — however it's triggered, including a crash — never loses anything that was already committed to `S`. Concretely:

1. Every write to `E` or `I` is durable at the moment it is acknowledged to the Interaction Shell — not batched for later flush. This is the runtime's translation of "capture is never blocked" into a durability guarantee: the researcher's mental model that "once I captured it, it's safe" must be literally true at the storage layer, not just at the UI layer.
2. `Session` checkpoints its Session Frame (current Investigation stage, accumulated in-progress content) at a bounded interval and at every stage transition — not only at Investigation completion. This bounds how much unwritten Investigation work a crash can cost.
3. `Cache` requires no shutdown action whatsoever. It is discarded implicitly.

### Crash Consistency

The runtime's crash-consistency guarantee is exactly as strong as its two irreplaceable planes and no stronger:

- `E` and `I` are written through an append-only, durable path (see _Persistence Boundaries_) such that a crash mid-write either leaves the previous valid state intact or completes the write — never a torn, partially-applied mutation. This is a direct runtime requirement of _Computational Principles_ Principle 2 (information is conserved) and Principle 11 (only legal transitions produce valid states): a torn write is not merely undesirable, it is not a member of the algebra at all, and the runtime must guarantee it cannot occur.
- `Session` recovery after a crash restores the Investigation to its last checkpoint, not its last keystroke. Content typed since the last checkpoint is lost — an explicit, bounded, and previously-justified loss (_Convergence Pass_: "the only things this component can lose are things that were never yet knowledge").
- `Cache` requires no recovery. It is rebuilt lazily.

## Event Flow

### The Interactive Loop — Single-Object, Foreground

```
Researcher action
    ↓
Interaction Shell classifies as Capture | Interpret | Navigate | IntentSubmit
    ↓
   Capture ──────────────→ Evidence Plane (append, durable, acknowledged)
   Interpret ─────────────→ Interpretation Plane (write, durable, acknowledged)
   Navigate ──────────────→ Projection Layer (read-only, may use warm or cold Cache)
   IntentSubmit ──────────→ Lifecycle Orchestrator Intent Queue
    ↓
Acknowledgment returned to researcher (sub-100ms target)
    ↓
Affected Cache regions marked dirty (asynchronous, does not block acknowledgment)
```

The critical property: **acknowledgment never waits on Cache invalidation, Emergence recomputation, or Synthesis.** A Capture is "done" the instant it is durable in `E`. Everything downstream is the Reconciliation Loop's problem, running after the fact.

### The Reconciliation Loop — Batch, Background

```
Scheduled trigger (elapsed interval, explicit researcher-initiated Review, or Intent Queue depth threshold)
    ↓
Synthesis Engine reads Evidence Plane (since its last stable snapshot) and current Interpretation Plane
    ↓
Synthesis produces:
    - revised Interpretation (confidence shifts, thread reassignment, Conflict Region open/close)
    - new Research Intent (deposited to Lifecycle Orchestrator's Intent Queue)
    ↓
Interpretation Plane updated (durable, attributed to this Synthesis run)
    ↓
Every Cache region dependent on changed (element, dimension) pairs marked dirty
    ↓
Relationship/Emergence Layer recomputes dirty regions of the graph (see Incremental Recomputation)
    ↓
Local Intelligence indices recompute dirty regions (independent, parallel, no ordering dependency on Emergence)
    ↓
Any open Projection subscribed to a now-dirty region re-renders (or is marked stale for on-demand re-render)
```

Synthesis is the only step here with write authority. Everything after it is pure recomputation from the new `S`.

### The Two Fast Lanes, Restated as Runtime Paths

The _Computational Model_ document already establishes that Capture and Interpret bypass the batch cycle by design, not as an optimization. The runtime consequence: **the Interactive Loop and the Reconciliation Loop are structurally incapable of blocking one another**, because the fast lanes write directly to the same planes the Reconciliation Loop reads from, with no shared mutex broader than "one write to one element or one (element, dimension) pair at a time." A Synthesis run reading `E` while a Capture is landing simply sees `E` as of the read's own snapshot boundary — it never sees a torn intermediate value, and it is not required to see the newest Capture (see _Synchronization Philosophy_).

## Semantic Update Pipeline

This is the answer to _"when the user edits one sentence, what recomputes."_

A single edit to the text of a Note Block is, algebraically, a **Supersede**: the old object is retained, a new object replaces it in every view, and provenance records the relationship (_Research Information Model_: "objects are immutable"; _Discovery Roadmap_: Supersede is a join-semilattice-respecting endomorphism of `E`). The runtime pipeline:

1. Interaction Shell packages the edit as `Supersede(old_id, new_content)`.
2. Evidence Plane appends the new object, records the supersession edge, leaves the old object untouched.
3. **Interpretation is not automatically copied.** The new object starts with no interpretation of its own; the runtime raises this as a visible, low-priority Research Intent ("newly superseded object lacks interpretation") rather than silently inheriting the old object's metadata unexamined — inheriting silently would let stale interpretation ride along on new evidence without anyone ever having asserted it applies. (This is an explicit engineering decision — see _Engineering Decisions_ below — not dictated by Phase 1/2 prose, which is silent on this point; it is also flagged in the Ambiguity Audit.)
4. Every Cache region that read the old object's identity is marked dirty: the Relationship/Emergence graph (any edge touching the old object), Local Intelligence indices (any index entry keyed on the old object's text), and any open Projection displaying the old object.
5. Nothing about this pipeline touches Synthesis. A single edit is a single-object event; it takes the fast lane. Synthesis only becomes relevant if the edit is significant enough that the researcher (or a scheduled Reconciliation pass) chooses to re-run reconciliation across the region.

### What Propagates When Semantic Meaning Changes

"Semantic meaning" in this architecture is not a mystical property — it is precisely the current value of `I` for a given element, and, downstream, whatever `f(S)` computes from it. So "meaning changes" always resolves to one of two concrete runtime events:

- **An Interpret write** (single coordinate, fast lane) — propagates only to Cache regions keyed on that (element, dimension) pair. Bounded, local invalidation.
- **A Synthesis write** (many coordinates, batch) — propagates to every Cache region keyed on any of the changed pairs. Potentially large, but never unbounded: it is bounded by the size of the Synthesis run's actual output, never by the size of `S` as a whole (see _Incremental Recomputation_).

There is no third propagation mechanism. Nothing "propagates" as a side effect of Capture alone, because new evidence with no interpretation yet attached changes nothing that any Cache region currently depends on — it simply becomes visible the next time something queries `E` directly (e.g., the Inbox).

## Dependency Updates & Invalidation Rules

### Dependency Tracking Granularity

The runtime tracks dependencies at the grain of **(element, dimension) pairs** for Interpretation reads and **element identity** for Evidence reads — never at the grain of "the whole graph" or "the whole Projection." This granularity is chosen deliberately: it is the finest grain that is still meaningful (a Projection cares about specific coordinates, not "some coordinate somewhere"), and it is exactly the grain at which `I` itself is defined as a function (_Discovery Roadmap §1_), so no translation layer is needed between "what changed" and "what depended on it."

Every derived structure — a graph edge, a Local Intelligence index entry, a Projection's rendered fragment — is registered with the set of (element, dimension) pairs and element identities it was computed from. This registration is not a manually maintained bookkeeping structure; it is a byproduct of the pure functions themselves (see _Caching Philosophy_).

### Invalidation Rules

1. Any write to `I(element, dimension)` invalidates every derived structure registered against that exact pair. It does not invalidate structures registered against other pairs of the same element, and it does not invalidate structures for unrelated elements.
2. A Supersede invalidates every derived structure registered against the superseded element's identity, and additionally raises the "interpretation not yet assigned" Intent described above.
3. A Capture invalidates nothing by itself (there is nothing yet depending on an element that didn't exist), but it enqueues an indexing job so that Local Intelligence's Indexing Service becomes aware of the new element before anything queries it.
4. Invalidation is monotonic within a single Reconciliation pass: once a region is marked dirty, it stays dirty until recomputed, even if further writes land in the interim — there is no "un-dirtying" outside of an actual recomputation completing.
5. Invalidation never touches `E` or `I` themselves. It only ever marks `Cache` entries. This is the runtime encoding of _Computational Principles_ Principle 5 ("derived information must remain disposable") — invalidation is precisely the mechanism by which "disposable" is made operational rather than aspirational.

## Caching Philosophy

Every cached structure in the system obeys one rule: **it must be expressible as `f(S)` (or, for Local Intelligence, `f(S, service-internal-parameters)`) for a deterministic, pure `f`.** This is not a style preference — it is the runtime's enforcement of the Substrate/derived distinction from _Computational Principles_ Principle 5 and the formal test given in _Discovery Roadmap §5_ ("X is derived iff X can be written as f(S) for deterministic f").

Consequences:

- **No cache is ever the only copy of anything.** Every cache can be deleted mid-operation and correctness is unaffected, only latency.
- **Caches never need conflict resolution.** Because they are pure functions of `S`, two independently computed copies of the same cache entry (e.g., on two machines, or before/after a crash) are either identical or one is stale — never divergent in a way that needs merging. Merging is a concept that applies to `E` and `I`; it is meaningless for `Cache`.
- **Cache warmth is a performance concern only, never a correctness concern.** A cold-started system with an empty Cache and a system that has been running for a year with a fully warm Cache must produce bit-identical Projection output for the same query against the same `S`. This is the runtime's version of the naturality condition on Projections (_Discovery Roadmap §3_): correctness must not depend on cache history.

### What Is Cached

|Structure|Function of|Rebuild cost class|
|---|---|---|
|Relationship/Emergence graph (full or partial)|`E`, `I`, similarity signals|Superlinear in dirty region size; see Incremental Recomputation|
|Local Intelligence indices (full-text, similarity)|`E` (text), `I` (coordinates)|Linear in dirty region size|
|Projection render output|Query definition + Abstraction parameter + slice of `S`|Cheap; recomputed on read if stale|
|Dashboard aggregate statistics|`I` (confidence, conflict, stage distributions)|Cheap; incremental counters where possible|

## Incremental Recomputation

Full recomputation of the Relationship/Emergence graph from scratch is always _correct_ but is not always _necessary_, and the runtime must not require it after every single write — that would make the fast lanes structurally dishonest (acknowledging a Capture instantly while secretly forcing an O(n²) graph rebuild before the next read is trustworthy).

The runtime's incremental model:

1. Every write carries a precise **change set**: the (element, dimension) pairs or element identities it touched.
2. The Relationship/Emergence Layer's Graph Assembly sub-component (_Internal Structure of Components_) recomputes only the edges whose weighting inputs intersect the change set. Because edge weight is a function of a bounded number of shared organisational dimensions per pair of elements (not of the whole graph at once), the affected edge set for a single Interpret write is bounded by "elements sharing at least one dimension value with the changed element" — not by the total element count.
3. For a Synthesis run touching many elements at once, the change set is simply larger, and recomputation is correspondingly larger — but it is still bounded by the Synthesis run's actual output size (_Semantic Update Pipeline_, above), never by `|S|` as a whole, because Synthesis itself only writes coordinates it has reason to touch.
4. A full recomputation is never _forbidden_ — it is always a legal (if wasteful) way to satisfy the same correctness guarantee, and the runtime uses it opportunistically during idle ticks if incremental bookkeeping has become fragmented enough that a rebuild is cheaper than continued incremental patching (a standard amortization trade-off, not a special case).

This gives the runtime a precise, falsifiable performance contract: **the cost of reflecting a single Interpret write is bounded by the local neighborhood of the changed element, not by the size of the project.** Any implementation for which this fails to hold has violated the runtime specification even if it remains philosophically compliant.

## Background vs. Foreground Processes

|Process|Loop|Blocks Interactive Loop?|Trigger|
|---|---|---|---|
|Capture / Interpret write|Interactive|No — is the loop|Researcher action|
|Navigation / Projection render|Interactive|No — is the loop|Researcher action|
|Local Intelligence indexing|Reconciliation|Never|New Capture, dirty text region|
|Similarity computation|Reconciliation|Never|Dirty (element, dimension) region|
|Relationship/Emergence recompute|Reconciliation|Never (reads may serve stale Cache meanwhile)|Dirty region, or on-demand at read-time if small enough|
|Synthesis Engine run|Reconciliation|Never; may run for seconds-to-minutes|Elapsed schedule, explicit Review invocation, or Intent Queue depth|
|Idle-tick housekeeping (opportunistic full rebuild, storage compaction)|Reconciliation|Never; yields immediately to any Interactive event|Idle timeout|

The invariant binding this table: **no process outside the Interactive Loop is ever permitted to hold a lock that a Capture or Interpret write would need to acquire.** Reconciliation processes read a stable snapshot of `S` and write their results as new, additional facts (new `I` coordinates, new Cache entries) — they never require exclusive access to `S` as a whole. This is a direct runtime consequence of `I` being a multi-value register (_Discovery Roadmap §3_): concurrent writes to the same coordinate are retained, not blocked.

## Rendering Pipeline

A "render" in this architecture is any output of the Projection functor: Dashboard, Semantic Map, Thread View, Timeline, Review Panel, or a maturity-scoped Publication view.

```
Query Definition (which question) + Abstraction Parameter (which resolution)
    ↓
Projection reads: Evidence Plane (slice) + Interpretation Plane (slice)
                  + Relationship/Emergence output (if the Query needs graph structure)
                  + Local Intelligence output (if the Query needs suggestions)
                  + Lifecycle Orchestrator active-session state (if the Query needs "what am I mid-way through")
    ↓
Render Cache checked: if a valid (unexpired-by-invalidation) entry exists for this exact
    (Query Definition, Abstraction Parameter, S-version) triple, return it
    ↓
Otherwise: recompute, store in Render Cache, return
```

Two rendering guarantees follow directly from the Substrate/derived distinction:

- **Naturality across abstraction levels.** Coarsening a Projection's Abstraction Parameter must commute with the Projection function — rendering at a coarse level and then noting what a finer level would add must agree with rendering at the fine level directly and coarsening the result (_Discovery Roadmap §3, §6_ — the filtration/coarsening poset). Any renderer whose coarse view can disagree with its fine view about the same underlying facts has broken this contract.
- **No render ever mutates anything it reads.** The rendering pipeline has no write path, structurally — this is why it is safe to run arbitrarily many concurrent renders (multiple open Projections, multiple abstraction levels of the same thread) without any coordination between them.

## Synchronization Philosophy

The system is local-first and, by the governing principles, has no mandatory server. Synchronization (where present, e.g., across a researcher's own multiple devices, or opt-in peer sharing) is therefore synchronization of `S` itself — not of Cache, not of Session, not of Queue.

- `E` synchronizes as a **join** — two independently-grown copies of the Evidence Plane merge by union, which is always well-defined because `E` is a join-semilattice (_Discovery Roadmap §3_). No conflict is possible in principle: two devices capturing different Note Blocks, or even both superseding the same object with different replacements, simply produce a merged `E` containing everything — a divergent double-supersession becomes a Conflict Region in `I`, exactly the same mechanism that already exists for scientific contradiction, rather than a special-cased sync conflict.
- `I` synchronizes as a **multi-value register**: concurrent, non-conflicting writes (different (element, dimension) pairs) merge trivially; concurrent conflicting writes (same pair, different values) are _retained, not overwritten_ — both values persist, tagged with their provenance, exactly as a Conflict Region would already require. Sync does not need a bespoke conflict-resolution algorithm; it needs to apply the same rule the Interpretation Plane already applies to concurrent Synthesis-vs-researcher writes on a single machine.
- `Cache` and `Queue` never synchronize. Each device rebuilds its own Cache from its own copy of `S` after a sync completes. This is correct by construction (Caching Philosophy, above) and avoids an entire category of distributed-cache-coherence problems the architecture has no need to solve.
- `Session` (in-progress Investigations) is device-local and does not synchronize by default — an in-progress Investigation is pre-formal scaffolding (_Discovery Roadmap §7_), and there is no requirement that it be visible anywhere until it crosses into `E` via the Completion Gate.

This gives synchronization a genuinely small surface: it is "merge two join-semilattices and one multi-value-register-valued function," a well-understood, already-necessary algebra — not a new subsystem bolted on afterward.

## Update Ordering

Given the above, the runtime's total ordering guarantees are deliberately weak where weakness is safe, and strict only where correctness demands it:

- **Within a single (element, dimension) pair, writes are causally ordered** by their `causality_token` — a later write that was formed against an earlier version always attaches its provenance to that earlier version, so the history of a single coordinate's evolution is always reconstructible.
- **Across different elements or different dimensions, writes have no required ordering.** The runtime never blocks one Capture to wait for another to "finish first" — this would violate the Interactive Loop's foreground guarantee for no correctness benefit, since unrelated elements cannot conflict.
- **Synthesis runs are strictly serialized against each other** (never two concurrent Synthesis passes over the same project) but are never serialized against Capture or Interpret — a Synthesis run simply reads whatever snapshot of `E`/`I` existed at the moment it began, and any Capture/Interpret landing during the run is picked up by the _next_ run, not lost, not blocked.
- **Cache recomputation has no ordering guarantee relative to other Cache recomputation** — the Relationship/Emergence Layer and Local Intelligence indices may finish in either order; nothing downstream depends on their relative completion time, only on each individually reflecting a `S`-version at least as new as what it's being read against (see Failure Recovery, staleness reporting).

## Failure Recovery

|Failure|Runtime response|
|---|---|
|`E`/`I` storage unreadable at startup|Halt before accepting Events; report explicitly. Never guess or silently initialize an empty state over a possibly-recoverable one.|
|Write to `E`/`I` fails mid-flight (disk full, power loss)|The write is defined to either not have happened or to have fully happened (see Crash Consistency) — the runtime never reports success for a write that didn't durably land.|
|Synthesis run crashes mid-pass|No partial Interpretation write is visible — a Synthesis run's output is committed as a single durable transaction, or not at all. A crashed run simply did not happen; the next scheduled run picks up the same accumulated Evidence.|
|Cache/index corruption detected|Discarded and rebuilt from `S`. Never "repaired in place" — repair-in-place would require trusting a corrupted structure's partial validity, which the architecture has no mechanism to verify cheaply, whereas full rebuild is always correct by definition.|
|Local Intelligence service crashes|Isolated to that service; Interaction Shell and Projection Layer degrade gracefully (no suggestions offered) rather than failing the surrounding Capture/Navigate action. This follows directly from Local Intelligence's "no authority" contract — nothing above it can be broken by its absence.|
|Investigation session data lost (uncheckpointed)|Explicit, bounded, previously-justified loss. Reported to the researcher as "resume from last saved point," not silently discarded.|

## Persistence Boundaries

Exactly two things cross the boundary into durable, crash-consistent storage as authoritative fact: `E` and `I`. Everything else — `Cache`, `Queue`, and (with the bounded exception of Session checkpoints) `Session` — may persist for performance or convenience but carries no correctness obligation if lost.

This boundary is not an implementation detail deferred to a later document — it is the direct runtime expression of the Contract Table in _System Architecture - Division of Responsibility_: "only the Evidence Plane and Interpretation Plane hold anything that would be a loss if deleted." The persistence layer's entire job is to make that sentence true under crash, concurrent access, and partial hardware failure — nothing more.

## Engineering Decisions

1. **Supersession does not carry forward interpretation automatically.** New evidence starts uninterpreted; this is surfaced as an Intent rather than silently inheriting old coordinates. _Rationale:_ silent inheritance would let unexamined interpretation attach to new evidence without any researcher or Synthesis run ever having asserted it applies — a violation of "every write to `I` is attributable" (_Computational Model_, Interpretation Plane invariants).
2. **Cache is never trusted across a restart without re-derivation being the default,** even if a serialized cache exists on disk. _Rationale:_ correctness must never depend on cache history (Caching Philosophy); trusting a stale serialized cache reintroduces exactly the class of bug — "the view disagrees with the state" — that the entire Substrate/derived split exists to prevent.
3. **Dependency tracking granularity is (element, dimension) pairs and element identity — not "whole graph" or "whole document."** _Rationale:_ this is the finest grain at which `I` is already defined as a function; any coarser grain would force unnecessary invalidation (recomputing things that didn't actually depend on what changed), and any finer grain has no meaningful referent in the algebra.
4. **Synthesis runs are serialized against each other but never against Capture/Interpret.** _Rationale:_ required by the multi-value-register semantics of `I` — concurrent conflicting writes are retained as Conflict Regions rather than blocked, so there is no correctness reason to make Capture/Interpret wait.

---

## Rejected Alternatives

- **A single global lock around `S` for every write.** Rejected: would serialize unrelated Captures against each other for no correctness benefit, directly violating the Interactive Loop's foreground latency guarantee and the (element, dimension)-grain concurrency the multi-value register model already supports.
- **Continuous, always-on Synthesis (a background daemon reinterpreting on every write).** Rejected explicitly by Phase 1 (_Experience & Interaction Specification_, "Review Mode... Synthesis is a deliberate act of review, not a background daemon silently rewriting meaning") and confirmed by the algebra: Synthesis is a closure operator whose idempotence is only meaningful relative to a _fixed_ `E` snapshot (_Discovery Roadmap §3_) — running it continuously against a constantly-moving `E` would make "has this converged" undefined.
- **Trusting a persisted Cache as authoritative on restart, skipping re-derivation for speed.** Rejected: violates the derived/authoritative distinction outright; a fast wrong answer is not an acceptable trade against a briefly slower correct one, especially since re-derivation can itself be made fast via incremental recomputation rather than full rebuild.
- **Ordering all writes through one global sequence number for simplicity.** Considered, rejected: would impose a false total order on causally unrelated writes (two Captures to unrelated Note Blocks), adding coordination cost with no corresponding correctness gain — causality tokens scoped per-element are sufficient and cheaper.

## Open Questions

1. **Exact Synthesis trigger policy** — elapsed-time schedule vs. Intent Queue depth vs. explicit-only. Phase 1 says "periodic... approximately weekly" as a UX cadence, not a runtime rule; the runtime should probably support a configurable policy rather than hardcoding one, but which defaults are correct is not yet decided. Deferred — this can be changed without touching the algebra.
2. **How large a "dirty region" must become before opportunistic full-rebuild beats incremental patching** is an empirical, implementation-specific tuning question, not an architectural one. Deferred to implementation.
3. **Whether Render Cache entries should be proactively warmed for the currently-open Projection during Reconciliation, or only recomputed lazily on next read** — a latency/throughput trade-off with no correctness implication either way. Deferred.
4. **The precise checkpoint interval for in-progress Investigations** (time-based, keystroke-count-based, stage-transition-only) is a UX/durability trade-off, not resolved here. Deferred; see _[[03-Ambiguity-Audit]]_ item on Session Frame durability.

## Implementation Consequences

- A persistence layer must support **append-only, crash-consistent writes** to two logically separate stores (`E`, `I`) with independent durability guarantees but a shared consistency requirement (an `I` write must never reference an `E` element that isn't itself durable).
- A dependency-tracking substrate (an incremental computation framework, in the spirit of the _Discovery Roadmap_'s translation-not-import stance toward reactive programming and incremental computation research) is required beneath the Relationship/Emergence Layer and Local Intelligence indices — not optional infrastructure, but the mechanism that makes the Incremental Recomputation section true rather than aspirational.
- The Interaction Shell's acknowledgment path must be architecturally decoupled from every Reconciliation-loop process — this is most naturally implemented as: durable write completes → acknowledge → enqueue invalidation as a fire-and-forget background task.
- Local Intelligence services must be process- or module-isolated such that their failure cannot propagate into the Interactive Loop (per Failure Recovery) — this argues for a service-boundary (in-process interface with enforced isolation, or true process boundary) rather than tightly-coupled library calls.
