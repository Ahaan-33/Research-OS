# ADR-0004: Enforce the Subsystem 2-only write boundary via package export surface and a lint rule, not a runtime guard

## Status

Accepted

*(This ADR is referenced by number in ADR-0001's rationale for choosing pnpm — "the same class of 'boundary enforced by absence, not convention' preference already used throughout the architecture (see ADR-0004)." That reference predates this document; this is the ADR it was pointing to.)*

## Context

_[[07-Transformation-Algebra]]_'s T-Functor and _[[02-System-Invariants]]_ INV-9/INV-11 establish, as a proven and load-bearing property, that **exactly one subsystem — the Transformation Engine (Subsystem 2) — may ever call `PersistentResearchState.commit`.** _[[16-Subsystem-Interface-Contracts]]_ states this at the interface level: "callable ONLY by Subsystem 2. No other subsystem's module is compiled against this method at all." _[[02-System-Invariants]]_'s own Engineering Decision 1 goes further, requiring this to be a structural (interface-shape) guarantee wherever possible, not a runtime-checked policy — "a runtime `if` that rejects an illegal write is strictly weaker than an interface that has no method through which the write could even be attempted."

TypeScript, the language fixed for the core library (_Reference Implementation Strategy_, Section 5), has no first-class mechanism for restricting a symbol's visibility to one specific consuming module within the same package the way, say, a `friend` declaration or an access modifier scoped to a named module would. Anything exported from a module's surface is importable by any other file in the same compilation unit that can resolve the path. Left unaddressed, "only Subsystem 2 calls `commit`" would be true only by convention — exactly the weaker guarantee Document 02 already rejected in the abstract, now concretely reappearing as a tooling gap once a real language is chosen.

## Decision

Two mechanisms, applied together, since neither alone gives the structural guarantee required:

1. **Package export surface.** Within `@ros/core`, the concrete implementation of `PersistentResearchState` (including `commit`) lives in an internal module (`packages/core/src/persistent-research-state/`) that is never re-exported from the package's public entry point (`packages/core/src/index.ts`). Only `TransformationEngine`'s own public methods (`capture`, `supersede`, `interpret`, `applySynthesisBatch`) are exported for consumption by `@ros/obsidian-plugin` or any other future consumer of `@ros/core`. This alone structurally prevents any *external* package from ever seeing `commit` exists — the same enforcement pattern _[[15-Canonical-Data-Model]]_ already used for D10.1/D10.2 (a value that doesn't type-check as `Element` cannot be constructed; a method that isn't exported cannot be called from outside the package).
2. **Internal import-boundary lint rule.** Export surface alone does not prevent a file *within* `@ros/core` — some future module added by a contributor unfamiliar with the invariant — from directly importing `persistent-research-state/commit` internally, bypassing `TransformationEngine`. A lint rule (`eslint-plugin-boundaries`, or an equivalent `no-restricted-imports` pattern configured per-directory) fails the build if any file outside `packages/core/src/transformation-engine/**` imports anything from `packages/core/src/persistent-research-state/**` beyond the read-only surface (`snapshot`, `getElement`, `getCoordinate`, `getDimension`, `currentElements`, `conflictRegions` — all of which _[[16-Subsystem-Interface-Contracts]]_ already authorizes for every subsystem to read). This rule runs in CI, not only as an editor hint, so a violation fails the same way a type error would.

Together, these two make "only Subsystem 2 writes" true for exactly the same reason T-Functor's proof holds: not because a check is present that could be forgotten or bypassed under pressure, but because the code path does not exist in what compiles and passes CI.

## Why not a runtime capability token instead (e.g., `commit` requires an unforgeable object only `TransformationEngine` holds a reference to)

Considered. A capability-token approach is strictly stronger in one respect — it would remain a real, runtime-enforced boundary even if `@ros/core` were later split across trust boundaries (e.g., a scenario where untrusted third-party code is loaded into the same process and could, in principle, reach into internal modules via reflection or a bundler that flattens module boundaries). For the current scope — a single package, developed and reviewed by one team, compiled by a standard TypeScript toolchain that respects module boundaries — this additional strength buys nothing yet: there is no untrusted code sharing the process, and the lint-plus-export-surface combination already makes the illegal call path unreachable in every code path that will actually ship. Introducing a capability token now would add a runtime indirection (`commit` taking and checking a token argument) to the one method whose type signature _[[16-Subsystem-Interface-Contracts]]_ already specifies cleanly, for a threat model not yet in scope.

**This is flagged explicitly as revisitable, not settled permanently**: if `@ros/core` is ever extended to load third-party plugins or user-supplied code into the same process (a scenario _[[12-System-Architecture-First-Draft]]_ and _Reference Implementation Strategy_ do not currently anticipate), the capability-token or a true process-boundary approach becomes necessary, and this ADR's reasoning would no longer hold — a future ADR should supersede this one at that point rather than silently patch around it.

## Consequences

- One additional lint rule and one directory-naming convention (`persistent-research-state/`, `transformation-engine/`) to maintain; documented in `CONTRIBUTING.md` so a new contributor understands *why* `commit` is unreachable from outside `transformation-engine/`, not just that it is.
- No runtime overhead — the enforcement is entirely compile-time/CI-time, consistent with Document 02's stated preference for structural over policed guarantees, now realized in the one concrete tool (a lint rule against a monorepo's package/module layout) available for it in this stack.
- If `@ros/core` is ever split into more than one package (rather than one package with internal directory boundaries, as ADR-0001 fixes for v0), this same boundary should be re-expressed as a true package-export boundary rather than a lint rule — a cheaper migration than it might sound, since the directory layout this ADR already establishes (`persistent-research-state/`, `transformation-engine/`) maps directly onto what would become two packages.
