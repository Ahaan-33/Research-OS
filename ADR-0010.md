# ADR-0010: Give `@ros/obsidian-plugin` its own `@types/node` and wall its TS project off from `native/`

## Status
Accepted

## Context

Reported regression, after ADR-0009 landed: `pnpm run build:native:electron`
and `pnpm test` both pass, but `pnpm run build` fails during
`tsc -p packages/obsidian-plugin --noEmit` with cascading
"Cannot find module" errors for `obsidian`, `node:path`, and `@ros/core` —
i.e. every import at the top of `src/main.ts`, built-in and workspace and
third-party alike, simultaneously unresolvable.

**What I verified, concretely, before writing this ADR:**

- A from-scratch reproduction (`unzip` the original archive, reapply every
  ADR-0007/0008/0009 change, `pnpm install` → `pnpm run build:native:electron`
  → `pnpm test` → `pnpm run build`, in that order, repeated including a
  second `pnpm install` after the isolated native build already existed)
  did **not** reproduce a build failure in this environment
  (pnpm 9.12, npm 10.9, Node 22, TypeScript 5.9.3): all three commands
  passed cleanly every time.
- I inspected `packages/obsidian-plugin/node_modules` before and after
  running the isolated `npm install` inside
  `native/electron-better-sqlite3` — the symlinks to `obsidian`,
  `better-sqlite3`, `esbuild`, `typescript`, and `@ros/core` were
  byte-identical and untouched.
- `pnpm-workspace.yaml`'s `packages/*` glob only ever resolved to 3
  workspace projects (root, `@ros/core`, `@ros/obsidian-plugin`) — the
  isolated `native/electron-better-sqlite3/package.json` was never picked
  up as a 4th workspace member, in any run.

So this ADR does not claim a definitively reproduced mechanism. What it
does do is close the two most plausible, environment-dependent gaps ADR-0009
opened, both of which are real regardless of whether they are *the*
trigger for the reported failure, and both are cheap, safe, and strictly
additive:

**Gap 1 — `@ros/obsidian-plugin` never declared its own `@types/node`.**
It has always type-checked `node:path` (and, transitively, `node`'s other
built-ins) successfully only because `@types/node` happened to be
resolvable via pnpm's dependency graph — installed as a devDependency of
the *sibling* `@ros/core` package, not of `@ros/obsidian-plugin` itself.
That is exactly the kind of implicit, workspace-layout-dependent
resolution that ADR-0007/0008/0009 already flagged as fragile in the
native-addon and migrations contexts (`__dirname`, `bindings()`
stack-walking) — here it's the same category of problem one layer up, in
TypeScript's own type resolution rather than Node's runtime module
resolution. Any pnpm version, install order, or hoisting-behavior
difference that changes how `@types/node` happens to become reachable
from `packages/obsidian-plugin` breaks `node:path` (and, once one global
type input is unresolvable, TypeScript's diagnostics for the rest of the
file — including unrelated imports in the same file — reliably degrade,
which is consistent with all three imports failing together).

**Gap 2 — nothing told `tsc -p packages/obsidian-plugin` to stay out of
`native/`.** ADR-0009 put a real, npm-installed `node_modules` tree
(better-sqlite3 and its transitive dependencies, several of which ship
their own bundled `.d.ts` files) physically inside
`packages/obsidian-plugin`, for the first time. `"include": ["src"]`
scopes root files correctly today, but there was no `"exclude"` making
that boundary explicit — leaving it implicit and dependent on `include`
never changing, rather than stated as a rule.

## Decision

**1. Add `@types/node` as an explicit devDependency of
`@ros/obsidian-plugin`**, matching the version `@ros/core` already pins:

```json
"devDependencies": {
  "@types/node": "^22.7.0",
  "esbuild": "^0.24.0",
  "obsidian": "^1.7.2",
  "typescript": "^5.6.0"
}
```

`node:path`'s types are now resolved the same, direct way for both
workspace packages — not incidentally, through a sibling package's
devDependency.

**2. Pin `"types": ["node"]` and add `"exclude": ["native"]` in
`packages/obsidian-plugin/tsconfig.json`:**

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": {
    "module": "esnext",
    "outDir": "dist",
    "rootDir": "src",
    "lib": ["ES2022", "DOM"],
    "types": ["node"]
  },
  "include": ["src"],
  "exclude": ["native"]
}
```

`"types": ["node"]` stops TypeScript's default "automatically include
every visible `@types/*` package" behavior — so a stray or duplicate
`@types` package reachable from anywhere in the resolution path (now
including a whole npm-installed tree ADR-0009 introduced) can't silently
join the global scope; only `@types/node`, requested explicitly, is
included. `"exclude": ["native"]` makes the boundary ADR-0009 relies on
implicit-via-`include` into an explicit, stated rule instead.

Both changes are additive and scoped entirely to
`packages/obsidian-plugin`'s own config; nothing about ADR-0009's
isolated-build architecture changes. Verified clean from scratch:
`pnpm install` → `pnpm run build:native:electron` → `pnpm test` (20/20)
→ `pnpm run build`, all passing together, including a repeat `pnpm install`
after the isolated native directory already has its own `node_modules`.

## Why not just re-run and assume it was a fluke

Even without a confirmed reproduction, both gaps above are pre-existing
latent fragility that ADR-0009 made materially worse (by adding a second,
foreign, npm-managed `node_modules` tree inside the same package
directory for the first time) — they're worth closing on their own
merits, in the same spirit as ADR-0007's closing principle: don't leave a
subsystem depending on an implicit, layout-dependent resolution when an
explicit one is one line away.

## Consequences

- `@ros/obsidian-plugin` no longer depends on `@ros/core`'s
  devDependencies for its own type-checking to succeed.
- Any future file added under `packages/obsidian-plugin/native/` (or any
  other non-source subdirectory) is excluded from the TS project by
  explicit rule, not by accident of what `include` currently says.
- If the reported failure recurs, the next debugging step should capture
  the exact `pnpm`/`npm`/`typescript` versions and a `tsc --traceResolution`
  (or `--extendedDiagnostics`) run, since this ADR could not reproduce it
  and therefore could not confirm the precise trigger — only close the
  most plausible gaps.
