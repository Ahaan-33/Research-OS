# ADR-0008: Locate migration files via an explicit path, not the bundle's `__dirname`

## Status
Accepted

## Context

Bug report, after ADR-0007's fixes were deployed and confirmed to resolve
the native-addon crash:

```
Error: Invalid package /app/resources/electron.asar
  at migrationFiles()
  at openStore()
  at ResearchOperatingSystemPlugin.onload()
```

Diagnostics:

```
__dirname       = /app/resources/electron.asar/renderer
MIGRATIONS_DIR  = /app/resources/electron.asar/renderer/migrations
process.cwd()   = /home/ahaan
fs.existsSync(MIGRATIONS_DIR) = false
```

`esbuild.config.mjs` (per ADR-0007 part 3) does copy
`packages/core/src/persistent-research-state/migrations/*.sql` into
`packages/obsidian-plugin/migrations/`, and that directory is physically
present in the installed plugin folder. The bundled code is simply never
looking there.

**Root cause.** ADR-0007 assumed `path.join(__dirname, 'migrations')`
would keep working post-bundling because "the bundle's `__dirname` is the
plugin's install directory." That premise is false in general, and this
trace disproves it directly: `__dirname` inside the running `main.js` was
`/app/resources/electron.asar/renderer` — a path inside Electron's own
packaged resources, not `.obsidian/plugins/ros`. `esbuild.config.mjs`
bundles with `platform: 'node'`, `format: 'cjs'`, so esbuild itself does
not rewrite or fake `__dirname`; it leaves the identifier as the one
Node's CommonJS module wrapper supplies at load time, derived from
whatever path the *host's* `require()`/module-loading call used to load
the file. That means `__dirname`'s value is a property of **how the host
(Obsidian, running inside Electron) chose to load `main.js`**, not a
property of where the plugin's files live on disk — and that loading
mechanism is not a documented, stable contract. It can legitimately
resolve differently across dev vs. packaged builds, platforms, or Obsidian
versions, including — as observed here — to a path associated with
Electron's own bundled resources rather than the vault's plugin directory.

In other words: this is the exact same failure mode ADR-0007 already
diagnosed and fixed for the native addon (`bindings()`'s stack-walking
assumed a per-module file identity that bundling destroys), recurring here
because the *fix* for migrations stopped short — it made sure the asset
was physically present next to `main.js`, but left the code trusting
`__dirname` to describe where "next to `main.js`" is, instead of asking
the one component that actually knows: Obsidian's own plugin manifest API.

## Decision

Apply the same pattern ADR-0007 already established for
`nativeBindingPath`: stop deriving the migrations path from `__dirname`
inside `db.ts`, and instead pass it in explicitly from `main.ts`, computed
from the plugin's manifest-reported install directory — the same
`pluginDir` value already used (and confirmed working) for the native
addon:

```ts
// packages/obsidian-plugin/src/main.ts
const vaultBasePath = (this.app.vault.adapter as unknown as { basePath: string }).basePath ?? '.';
const pluginDir = path.join(vaultBasePath, this.manifest.dir ?? '.obsidian/plugins/ros');
const nativeBindingPath = path.join(pluginDir, 'better_sqlite3.node');
const migrationsDir = path.join(pluginDir, 'migrations');
this.store = openStore(dbPath, nativeBindingPath, migrationsDir);
```

```ts
// packages/core/src/persistent-research-state/db.ts
export function openStore(filePath: string, nativeBindingPath?: string, migrationsDir?: string): Store {
  ...
  const dir = migrationsDir ?? DEFAULT_MIGRATIONS_DIR; // __dirname-based fallback, test suite only
  const files = migrationFiles(dir);
  ...
}
```

`migrationsDir` is optional and defaults to the old `__dirname`-based path
only so the unbundled Vitest suite (plain Node, `openStore(':memory:')`,
no bundling involved) keeps working unchanged. The Obsidian plugin must
always supply it explicitly, exactly as it already must for
`nativeBindingPath`.

No change to `esbuild.config.mjs` is needed: it already copies the
migrations into `packages/obsidian-plugin/migrations`, i.e. next to
`main.js`, which is exactly where `pluginDir`-derived `migrationsDir` now
points.

## Why not fix this by changing how/where esbuild bundles, or by switching module systems

Considered. The failure isn't in how the code is bundled (`format: 'cjs'`
is correct and esbuild is not corrupting `__dirname`) — it's in trusting a
Node-level, host-mediated variable to answer a question ("where is my
plugin installed?") that Obsidian's own `Plugin` API already answers
directly and reliably via `this.manifest.dir` plus the vault adapter's
`basePath`. Changing bundler settings would not address that; it would
just change *which* incidental value `__dirname` happens to take on next,
without removing the dependency on an unspecified contract.

## Why not read migrations from `process.cwd()` or search for them

`process.cwd()` in the reported trace is `/home/ahaan` — the user's home
directory, unrelated to either the vault or the plugin. It reflects
whatever directory the Electron/Obsidian process itself was launched
from, not plugin-specific state, and is even less reliable than
`__dirname` for this purpose. Searching the filesystem for a directory
named `migrations` was rejected as unnecessary indirection: the plugin
already knows its own install directory unambiguously via the manifest
API; no discovery mechanism is needed.

## Consequences

- `openStore()`'s signature grows a third optional parameter
  (`migrationsDir`), mirroring `nativeBindingPath`. Existing test-suite
  call sites (`openStore(':memory:')`) are unaffected.
- The general principle ADR-0007 already wrote down in its Consequences
  section — "never rely on a bundled module's `__dirname`... resolve
  explicitly relative to the plugin's own installed directory" — is now
  actually applied consistently to both runtime assets the plugin ships
  (the native addon and the migrations), not just the first one.
- Any future asset needing a bundler/host-safe runtime path should follow
  the same shape: compute it once from `pluginDir` in `main.ts` (the only
  place with access to `this.manifest`), and pass it down explicitly
  rather than letting a lower layer infer it from `__dirname`,
  `process.cwd()`, or module-resolution introspection of any kind.
