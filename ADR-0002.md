# ADR-0002: better-sqlite3 as the v0 storage driver; mobile explicitly deferred

## Status

Accepted (desktop). Mobile support: explicitly out of scope, not solved.

## Context

_Reference Implementation Strategy_ (vault, Phase 6 Doc 4), Sections 4–5, fixes SQLite as the persistence engine and `better-sqlite3` as the concrete TypeScript driver, reasoning from atomicity (`commit`'s all-or-nothing requirement, D10) and from Capture's latency path needing no unnecessary async overhead. The same document's Section 2, comparing delivery forms, lists "cross-platform (desktop + mobile) for free" as one of the Obsidian plugin's advantages over a standalone app.

These two decisions are in tension, and Doc 17 does not surface it: `better-sqlite3` is a native Node addon (compiled per platform/ABI via `node-gyp` or prebuilt binaries). Obsidian Mobile runs plugins inside a Capacitor-based JavaScript environment with no Node runtime and no native module loading. A plugin depending on `better-sqlite3` cannot load on Obsidian Mobile at all — not slowly, not with degraded behavior, but with an immediate module-resolution failure. Doc 17's "mobile for free" claim was true of Obsidian generally; it stops being true the moment a native storage driver is chosen underneath it, and Doc 17 never revisited that claim once Section 5 committed to the driver. This ADR exists to state that plainly and resolve it, rather than let it surface later as a support ticket from a mobile user.

## Decision

v0 targets **desktop only**. `better-sqlite3` is used exactly as Doc 17 specifies, with no compromise to its API for the sake of mobile compatibility.

This is a narrowing of scope, not a reversal of Doc 17: Doc 17's own Section 7 ("Recommended First-Implementation Scope") never actually listed mobile support as a v0 deliverable — the "mobile for free" line appeared only in Section 2's general comparison of delivery forms, evaluating Obsidian-the-platform in the abstract, before the storage driver was chosen in Section 4. This ADR simply makes explicit that Section 2's claim does not survive Section 4's decision, and records the v0 scope accordingly rather than leaving the two sections silently inconsistent.

**For future mobile support**, the path is already open by construction: _Canonical Data Model_ (Doc 15) and _Subsystem Interface Contracts_ (Doc 16) specify `PersistentResearchState`'s schema and interface in storage-technology-independent terms — Doc 17 itself notes "Document 15's schema is engine-agnostic... a future server-backed engine is a swap, not a redesign." A WASM SQLite build (e.g., `sql.js` or a WASM binary with a persistent-storage-backed virtual file system) implementing the identical `PersistentResearchState` interface is the natural mobile-compatible substitute. This ADR does not build it, size it, or select among WASM options — it only records that doing so is a swap behind an already-fixed interface, not a redesign, and defers the actual choice to a future ADR once mobile is prioritized.

## Why not adopt a WASM engine uniformly now, for both platforms, avoiding the fork entirely

Considered and rejected for v0. A WASM SQLite build with durable, crash-consistent persistence on desktop requires a virtual file system layer that is markedly less mature and more fragile than `better-sqlite3`'s direct, battle-tested native file I/O — introducing that fragility into the one code path where atomicity is a hard, proven requirement (D10's commit-or-reject guarantee) would trade a real, working desktop implementation for a shakier one, purely to avoid maintaining two backends. Doc 17's stated goal for v0 is "the smallest implementation that faithfully validates the architecture," not "the smallest implementation that also solves mobile" — and _[[12-System-Architecture-First-Draft]]_'s own Method warns against exactly this kind of unforced complexity, taken on before it's required.

## Consequences

- Obsidian Mobile users cannot install or run ROS in v0. This must be stated in the plugin's manifest/listing description before any public release — discovered in a store listing, not in a crash report.
- Packaging must produce prebuilt `better-sqlite3` binaries for each desktop OS/arch combination Obsidian Desktop's bundled Electron/Node ABI requires (Windows, macOS, Linux; x64 and arm64) — a concrete build-pipeline task, tracked at implementation time, not resolved further here.
- A future ADR (not yet written) is required before mobile work begins, to select and validate a specific WASM engine against the same conformance tests this ADR's sibling, ADR-0005, establishes for the native driver.
