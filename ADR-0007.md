# ADR-0007: Load better-sqlite3's native addon via an explicit path, not `bindings()`'s auto-resolution; ship the addon and migrations next to `main.js`

## Status
Accepted

## Context

Bug report (verbatim facts, reproduced below in diagnostic form): the plugin builds, is discovered by Obsidian, and crashes during `onload()` before any database interaction, with:

```
TypeError: Cannot read properties of undefined (reading 'indexOf')
  at bindings.getFileName()
  at bindings(...)
  at new Database()
  at openStore()
  at ResearchOperatingSystemPlugin.onload()
```

**Root cause, confirmed by reading the installed `better-sqlite3@11.10.0` source (`lib/database.js`) directly:**

```js
let addon;
if (nativeBinding == null) {
  addon = DEFAULT_ADDON || (DEFAULT_ADDON = require('bindings')('better_sqlite3.node'));
} else if (typeof nativeBinding === 'string') {
  const requireFunc = typeof __non_webpack_require__ === 'function' ? __non_webpack_require__ : require;
  addon = requireFunc(path.resolve(nativeBinding).replace(/(\.node)?$/, '.node'));
}
```

When `options.nativeBinding` is not supplied (ADR-0002/ADR-0003's original code — `new Database(filePath)`, no options), `better-sqlite3` calls the `bindings` npm package's factory function, which locates the compiled `.node` file by **inspecting the call stack** (`getFileName()`, walking `CallSite` objects via `Error.prepareStackTrace`) to find "the file that called `bindings()`" and resolving the addon path relative to it. This mechanism assumes each module has its own distinguishable file in the stack trace — true under normal `node_modules`-based `require()`, false once `esbuild` collapses `@ros/core` and `better-sqlite3`'s JS wrapper into a single `main.js`: every frame in the stack shares the same file, so `bindings`'s internal logic cannot determine which frame is "the caller," `getFileName()` returns `undefined`, and the very next line (`fileName.indexOf(fileSchema)`) throws — exactly the reported trace, exactly the reported point ("before any database interaction," "occurs inside bindings").

**A second, related problem was found while verifying this fix end-to-end (not part of the original bug report, but blocking the same code path once the above is fixed):** `db.ts` locates its SQL migrations via `path.join(__dirname, 'migrations')`. `tsc` does not copy `.sql` files into `dist/`, and once bundled, `__dirname` inside `main.js` resolves to `main.js`'s own installed directory (esbuild does not preserve each original source module's individual directory when collapsing everything into one file) — not to `packages/core/src/persistent-research-state/`, where the migrations actually live in the repo. Left unfixed, the plugin would crash on the very next line after the `bindings()` fix, with `ENOENT` on the migrations directory, for the same underlying reason: a runtime path assumption that only held before bundling.

Both were confirmed by direct reproduction: building the actual bundle, copying only the artifacts a naive fix would produce, and running `onload()` against a mocked Obsidian host — first reproducing each failure, then confirming its absence after the corresponding fix.

## Decision

**1. Bypass `bindings()`'s auto-resolution entirely** by supplying `nativeBinding` explicitly:

```ts
// packages/core/src/persistent-research-state/db.ts
export function openStore(filePath: string, nativeBindingPath?: string): Store {
  const db = new Database(filePath, nativeBindingPath ? { nativeBinding: nativeBindingPath } : undefined);
  ...
}
```

`nativeBindingPath` is omitted in the test suite (plain Node via Vitest, unbundled — `bindings()`'s stack-walking works correctly there, so there is nothing to route around) and supplied explicitly by the Obsidian plugin, which is the only context where bundling occurs.

**2. Ship the compiled addon next to `main.js`**, and resolve its path at runtime relative to the plugin's own installed directory — not `node_modules` (Obsidian plugins ship as flat files; there is no `node_modules` at install time):

```ts
// packages/obsidian-plugin/src/main.ts
const pluginDir = path.join(vaultBasePath, this.manifest.dir ?? '.obsidian/plugins/ros');
const nativeBindingPath = path.join(pluginDir, 'better_sqlite3.node');
this.store = openStore(path.join(pluginDir, 'state.sqlite'), nativeBindingPath);
```

`esbuild.config.mjs` copies `better_sqlite3/build/Release/better_sqlite3.node` (resolved via `require.resolve('better-sqlite3/package.json')`, not a hardcoded path) to `packages/obsidian-plugin/better_sqlite3.node` as a build step immediately after bundling.

**3. Ship the migrations directory next to `main.js` the same way**, for the same reason (a physical file the compiler doesn't move, needed at a path relative to wherever the bundle actually runs from): `esbuild.config.mjs` copies `packages/core/src/persistent-research-state/migrations/*.sql` to `packages/obsidian-plugin/migrations/`. No code change to `db.ts`'s `MIGRATIONS_DIR` logic was needed — `path.join(__dirname, 'migrations')` already resolves correctly in both contexts once the files are physically present relative to `__dirname` in each: the test suite's `__dirname` is the real source directory (migrations already live there); the bundle's `__dirname` is the plugin's install directory (migrations now copied there too).

## Why not mark `better-sqlite3` external instead of bundling its JS wrapper

Considered. This would sidestep the stack-collapsing problem by leaving `require('better-sqlite3')` as a literal call in `main.js` — but Obsidian plugins are not installed via a package manager; there is no `node_modules/better-sqlite3` at the install location for that `require` to resolve against. Externalizing would trade one crash (`bindings()` failing) for another (`MODULE_NOT_FOUND`) without shipping the dependency's files regardless — at which point explicit `nativeBinding` is still required to avoid re-triggering the original failure, making externalization strictly additional work for no benefit over the chosen fix.

## Why not patch or vendor a fixed copy of the `bindings` package

Considered and rejected: `better-sqlite3` already provides the exact escape hatch this fix uses (`nativeBinding`, including an explicit comment in its own source referencing the equivalent Webpack workaround — `__non_webpack_require__`), for precisely this class of bundler incompatibility. Patching a transitive dependency to fix a problem its own direct dependent already exposes a supported option for would be unnecessary surface area.

## Consequences

- Packaging is no longer "copy `manifest.json` and `main.js`" (as ADR-0002/README previously stated) — it is "copy `manifest.json`, `main.js`, `better_sqlite3.node`, and `migrations/`." README updated accordingly.
- The copied addon is single-platform (whatever machine ran `pnpm build`), consistent with — and not a new limitation beyond — ADR-0002's existing desktop-only, single-build-machine scope for v0. Multi-platform prebuilt-binary packaging remains the future work ADR-0002 already flagged; this ADR does not extend that scope, only makes the existing single-platform binary actually loadable at runtime.
- Any future subsystem needing a bundler-safe runtime asset path (not just this one addon and this one migrations directory) should follow the same pattern established here: copy the physical file next to `main.js` at build time, resolve its path explicitly relative to the plugin's own installed directory at runtime — never rely on a bundled module's `__dirname`, `require.resolve`, or stack introspection reflecting its pre-bundling location.
